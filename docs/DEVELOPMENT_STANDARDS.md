# Standard di sviluppo Edilcom Gru

Leggere questo documento e le guide pertinenti in `node_modules/next/dist/docs/` prima di ogni modifica. Leggere il codice corrente e il README prima di pianificare un intervento.

- **Prototipo:** questo progetto è solo UI. Prezzi, stock, compatibilità, immagini e calcoli sono fixture illustrative. Non inventare regole commerciali, recapiti, garanzie, partnership, integrazioni, backend o pagamenti. Non presentare dati demo come verificati. Mantenere `noindex, nofollow` fino a esplicita autorizzazione alla pubblicazione.
- **Design:** ogni modifica UI riusa i componenti esistenti e preserva identità, palette, tipografia, spaziature, layout desktop e viewport supportati. Un redesign richiede autorizzazione esplicita. Nessuna freccia decorativa nelle CTA.
- **Responsabilità:** una sola implementazione per card, filtri, ricerca, ordinamento e riepiloghi condivisi. Separare fixture, funzioni pure e presentazione; evitare duplicazioni, componenti monolitici e astrazioni senza uso concreto.
- **TypeScript:** mantenere `strict`, tipi espliciti alle interfacce e controlli sugli input esterni; niente `any`, asserzioni non motivate o errori soppressi per aggirare i controlli.
- **CSS:** usare token condivisi, selettori mirati e file per responsabilità. Consolidare regole duplicate rispettando cascata, media query e specificità. Evitare override accumulati e `!important` senza motivo documentato nel codice. Verificare hover, focus e assenza di cambiamenti di layout indesiderati.
- **Semantica e accessibilità:** usare link per navigare e bottoni per azioni. Form con label, validazione e messaggi leggibili; tastiera e focus visibile per menu, filtri, dialog e gallerie. Gestire Escape, ripristino del focus, stati vuoti, caricamento, errori e controlli disabilitati. Non lasciare CTA senza comportamento reale nel prototipo.
- **Stato UI:** URL, controlli, risultati e reset devono concordare, anche con clic rapidi, back/forward e parametri non validi. Stock coerente tra badge, filtri, dettaglio e carrello; impedire aggiunte di prodotti esauriti anche nella funzione client. Nessun dato personale nei log o in localStorage.
- **Immagini e prestazioni:** file locali, dimensioni dichiarate, alt utili e fallback. Caricare in modo differito le immagini fuori schermo, ottimizzare i nuovi asset e registrare fonte/licenza nel manifest degli asset. Non attribuire foto dimostrative a prodotti reali. Nessuno scraping massivo. Evitare fetch, librerie e rerender inutili.
- **SEO:** un H1 per pagina, title e description coerenti, slug stabili, breadcrumb e link interni navigabili. Canonical solo verso contenuti realmente equivalenti; combinazioni di filtri non equivalgono arbitrariamente a una directory. Niente sitemap indicizzabili nella demo; structured data solo con informazioni veritiere, senza offerte/stock demo presentati come reali.
- **Sicurezza e dipendenze:** niente segreti nel client o nel repository. Validare query e riferimenti prodotto contro le fixture. Versioni esatte coerenti con lockfile e Node dichiarato; aggiungere dipendenze solo quando necessarie.
- **Verifica:** test pertinenti per funzioni pure di catalogo, ranking, stock, URL, paginazione e calcoli. Eseguire `npm ci`, lint, typecheck, test e build per consolidamenti; per modifiche mirate eseguire i controlli proporzionati. Verificare in browser i flussi modificati, i link e le regressioni visive. Dichiarare verifiche realmente eseguite e limiti rimasti, senza report superflui.
